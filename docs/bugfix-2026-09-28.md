## Bug 1：`QuestionRegistry.clear()` 误触发"提问超时"通知

**位置**：`src/core/questions.ts` → `QuestionRegistry.clear()`

**现状**：
```ts
clear(reason: string): void {
    for (const entry of [...this.#pending.values()]) {
        this.#log.info(`远程提问 ${entry.id} 因 ${reason} 取消`);
        entry.settle({ id: entry.id, items: [], answeredBy: "", raw: "" });
        entry.onTimeout(entry);   // ← 问题
    }
    this.#pending.clear();
    this.#latest = undefined;
}
```

**问题分析**：
- `entry.settle(...)` 已经通过 `onSettled` 把空答案递给了 `runAskRace` 的 racer，
  racer 走"无人回答"分支：`localAbort.abort()` + 返回 `buildAskTimeoutResult()`，
  turn 不会卡住、模型自行决定——这是 `clear()` 想要的效果，已经达成。
- 紧接着的 `entry.onTimeout(entry)` 额外调用了 `bridge.#questionTimeout()`，
  向钉钉**推送一条"提问超时"卡片**。但调用 `clear()` 的场景是
  `release()`（`/dingtalk release` 解除接管）和 `dispose()`（会话退出），
  根本不是超时——用户会收到一条莫名其妙的"提问超时了"通知。
- 对照组：`ApprovalRegistry.clear()` 刻意**不**调 `onExpired`，只打日志清掉。
  两边行为不一致，questions 这边是错的。

**修复方案（最小改动）**：删掉 `clear()` 里的 `entry.onTimeout(entry);` 一行。
- settle 的空答案已足以驱动 racer 收尾（关本地框、交回模型），turn 不阻塞；
- 不再产生虚假的超时推送；
- 与 `ApprovalRegistry.clear()` 的语义对齐。

**不做的（记录为后续优化）**：
- racer 目前无法区分"超时"与"被取消"：`clear()` 后本地对话框仍会被 abort，
  模型拿到的是 timeout 文案的结果（"DingTalk remote question #X timed out"）。
  更精细的做法是把取消原因透过 `settle` 传给 racer，release 时保留本地对话框
  让用户直接在终端回答。但那是行为级改动，本次只修"虚假通知"这个明确 bug，
  不扩大范围。

**回归测试**（`test/smoke.ts` [37]，端到端）：
- 发起一个双端提问（mock ask），执行 `/dingtalk release`，断言 ask 调用正常
  返回（`details.timedOut === true`，turn 不卡住），且没有新增"提问超时"卡片；
- 对照：自然超时仍推送超时卡片（已有用例覆盖：`timeoutMs: 300`，registry
  有 5 秒保底，实等 5 秒）。

## Bug 2：审批关键词吞掉待回答的提问

**位置**：`src/platforms/dingtalk/router.ts` → `CommandRouter.handle()`

**现状**：
```ts
if (APPROVE_WORDS.has(word) || DENY_WORDS.has(word)) {  // "同意/批准/通过/ok/yes/y…"
    await this.#handleApproval(message, word, rest);
    return;   // ← 无论有无待审批都直接 return
}
…
if (this.#deps.questions.size > 0) {   // 待回答提问走这里，但到不了
    await this.#handleAnswer(message, text);
    return;
}
```

**问题分析**：
- 当**只有待回答的提问、没有待审批**时，用户回"同意"（对是非题是非常自然的回答），
  `#handleApproval` → `approvals.resolve()` 失败 → 回"⚠️ 没有匹配的审批"并 return，
  提问永远得不到回答。复现条件很常见：双端提问 pending 时用户在手机上回"好的/同意"。
- 即使有待审批，"同意"也可能本意是回答提问——但这是固有歧义，审批优先是
  fail-closed 的安全选择（危险操作不能因歧义被放行），**保持审批优先**。

**修复方案**：审批分支加 `approvals.size > 0` 门控：
```ts
const hasPendingApprovals = this.#deps.approvals.size > 0;
if ((APPROVE_WORDS.has(word) || DENY_WORDS.has(word)) && hasPendingApprovals) {
    await this.#handleApproval(message, word, rest);
    return;
}
```
- 无待审批时，"同意/yes/ok" 落到后面的提问分支：`#handleAnswer` → `parseQuestionAnswer`
  走 customInput（单问题）或按规则解析，提问正常被回答；
- 有待审批时行为不变（审批优先，歧义时安全）；
- 改动一行判断，无新分支，风险最小。

**回归测试**（`test/smoke.ts` [36]，端到端）：
- 先 release→takeover 重建 stream（`MockSocket.instances` 是全局的，避免被
  fresh-module 测试污染），发起一个双端提问（mock ask），无待审批时用最新
  socket 发"同意"，断言提问被回答（`details.customInput === "同意"`），
  且**没有**收到"没有匹配的审批"回复；
- 对照：有待审批时"同意"仍走审批（已有用例覆盖，不破坏）。
